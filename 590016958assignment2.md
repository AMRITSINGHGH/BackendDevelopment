# Part A — Theory

## 0. JSON vs JSONB (storage format, write speed, query/index speed)

PostgreSQL has two JSON types. They accept the same input but store it differently.

| Point | `json` | `jsonb` |
|---|---|---|
| Storage format | **Text.** The exact input string is saved as it is (spaces, key order and duplicate keys are kept). | **Binary.** The input is parsed and saved in a decomposed binary form. Spaces are dropped, key order is not kept, and for duplicate keys only the last one is kept. |
| Write speed | **Faster.** Nothing to parse and convert, the text is just stored. | **Slightly slower.** The text must be parsed and converted to binary on every insert/update. |
| Query speed | **Slower.** The text must be re-parsed every time you read a key from it. | **Faster.** It is already parsed, so keys are found directly without re-parsing. |
| Indexing | Cannot be indexed directly (only with expression indexes). | Supports **GIN** indexes and operators like `@>` and `?`. |
| Typical use | Keep an exact copy of the incoming text (logs, audit). | Almost every other case: searching, filtering, updating. |

**Summary:** `json` is a bit cheaper to write; `jsonb` costs a little more on write but is much faster to query and can be indexed. For an application that reads or filters on JSON data, use `jsonb`.

## 1. How can PostgreSQL work as both a SQL and a NoSQL database in the same table?

A table can have normal **strictly typed columns** for the data that every row has, and one **`jsonb` column** for the data that changes from row to row.

- The typed columns (`id`, `name`, `price`) give the usual SQL benefits: data types, `NOT NULL`, `CHECK`, primary keys, foreign keys, joins.
- The `jsonb` column works like a document in a NoSQL database: every row can have different keys, nested objects and arrays, and no `ALTER TABLE` is needed to add a new attribute.
- Both parts are used in **one SQL query**, in one transaction.

**Example schema** (a product catalogue: laptops, books and phones all have different attributes):

```sql
CREATE TABLE products (
    id          SERIAL PRIMARY KEY,
    name        TEXT          NOT NULL,
    category    TEXT          NOT NULL,
    price       NUMERIC(10,2) NOT NULL CHECK (price >= 0),
    attributes  JSONB         NOT NULL DEFAULT '{}'::jsonb,
    CHECK (jsonb_typeof(attributes) = 'object')   -- must be a JSON object, not a list or number
);
```

| id | name | category | price | attributes (jsonb) |
|---|---|---|---|---|
| 1 | Dell XPS 15 | laptop | 145000.00 | `{"cpu": "i7", "ram_gb": 16}` |
| 3 | Clean Code | book | 499.00 | `{"author": "Robert C. Martin", "pages": 464}` |

A laptop has `cpu` and `ram_gb`, a book has `author` and `pages`, but they live in the same table. The fixed part is strict SQL and the variable part is flexible NoSQL.

## 2. `jsonb` operators with examples

Assume this row exists:

```sql
-- attributes for one product
'{"brand": "Dell", "wireless": true, "specs": {"cpu": "i7", "ram_gb": 16}}'
```

| Operator | Query | Value it returns |
|---|---|---|
| `->` | `SELECT attributes -> 'brand' FROM products WHERE id = 1;` | `"Dell"` (type **jsonb**, with quotes) |
| `->>` | `SELECT attributes ->> 'brand' FROM products WHERE id = 1;` | `Dell` (type **text**, no quotes) |
| `@>` | `SELECT attributes @> '{"wireless": true}' FROM products WHERE id = 1;` | `true` (boolean: left side contains the right side) |
| `?` | `SELECT attributes ? 'wireless' FROM products WHERE id = 1;` | `true` (boolean: the top-level key exists) |

(If a key is missing, `->` and `->>` return `NULL`, and `?` returns `false`. Some drivers treat `?` as a parameter placeholder; in that case use the function form `jsonb_exists(attributes, 'wireless')`.)

### Difference between `->` and `->>`

- `->` returns **jsonb**. The result is still JSON, so you can keep going deeper:
  `attributes -> 'specs' -> 'cpu'` returns `"i7"` (jsonb).
- `->>` returns **text**. This is a plain value, so it is used in `WHERE`, `ORDER BY`, and can be cast:
  `attributes -> 'specs' ->> 'ram_gb'` returns `16` as text, and `(attributes -> 'specs' ->> 'ram_gb')::int >= 16` compares it as a number.

Rule of thumb: use `->` in the middle of a path and `->>` at the end when you want the final value as text.

## 3. How can a GIN index on a `jsonb` column change query performance?

Without an index, a query on `attributes` has to do a **sequential scan**: read every row and look inside every JSON value. This gets slow as the table grows.

A **GIN (Generalized Inverted Index)** stores every key and value found inside the JSON and points to the rows that contain them, like the index at the back of a book. The planner can then jump straight to the matching rows.

```sql
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);
```

**Queries it speeds up:** containment and key-exists on any key in the document, for example

```sql
SELECT name FROM products WHERE attributes @> '{"wireless": true}';   -- uses the GIN index
SELECT name FROM products WHERE attributes ? 'wireless';              -- uses the GIN index
```

(The default GIN operator class supports `@>`, `?`, `?|`, `?&`. The smaller `jsonb_path_ops` class supports only `@>` but is faster and smaller.)

**A query it does NOT help with:** a comparison on a value pulled out with `->>`, such as

```sql
SELECT name FROM products WHERE (attributes ->> 'ram_gb')::int >= 16;  -- GIN is NOT used
```

GIN does not understand `->>` with `>=`, ranges or `LIKE`. For that, create a normal B-tree **expression index**:

```sql
CREATE INDEX idx_products_ram ON products (((attributes ->> 'ram_gb')::int));
```

**Cost:** a GIN index makes reads faster but makes writes slower and uses extra disk space, because the index must be updated on every insert/update.

## 4. Where could PostgreSQL + `jsonb` replace a MongoDB deployment, and where is MongoDB still better?

**PostgreSQL + `jsonb` can replace MongoDB when** the data is partly structured and partly flexible (like the product catalogue), the application needs strong consistency and joins, the data size fits on one big server (plus read replicas), and the team wants a single database to manage instead of two.

**MongoDB is still the better fit when** the whole application is document-oriented with deeply nested data, the data is very large and must be spread over many machines, or write traffic is extremely high.

| Point | PostgreSQL + `jsonb` | MongoDB |
|---|---|---|
| **Transactions** | Full ACID across any tables and rows, very mature. Strong point. | Multi-document ACID transactions exist (replica sets/sharded clusters), but they are heavier and less commonly relied on. The design usually keeps related data in one document to avoid them. |
| **Joins** | Real SQL joins between tables and `jsonb` data. Strong point. | No real joins; `$lookup` exists but is limited and slower. Data is usually embedded or de-normalised. |
| **Schema enforcement** | Typed columns, `NOT NULL`, `CHECK`, foreign keys, plus constraints on the JSON part. Strict where you want it. | Schema-less by default. Optional JSON Schema validation can be added per collection. |
| **Horizontal scaling** | Mainly scale **up** (bigger server) and scale reads with replicas. Partitioning helps; sharding needs extra tools (e.g., Citus). | Built-in **sharding** and replica sets. Scales out across many servers natively. Strong point. |
| **Updating part of a document** | Updating one key rewrites the whole `jsonb` value, which is costly for very large documents. | Updates a single field inside the document in place. |

**Conclusion:** use PostgreSQL + `jsonb` for hybrid relational/flexible data with transactions and joins; keep MongoDB for huge, horizontally-scaled, document-first workloads.

## Task 3 — Query by category-specific attribute (one query per category)

```sql
-- laptop: at least 16 GB RAM
SELECT name, attributes ->> 'cpu' AS cpu
FROM products
WHERE category = 'laptop'
  AND (attributes ->> 'ram_gb')::int >= 16;
-- result: Dell XPS 15 | i7

-- book: more than 300 pages
SELECT name, attributes ->> 'author' AS author
FROM products
WHERE category = 'book'
  AND (attributes ->> 'pages')::int > 300;
-- result: Clean Code | Robert C. Martin

-- phone: supports 5G
SELECT name
FROM products
WHERE category = 'phone'
  AND (attributes ->> 'has_5g')::boolean = true;
-- result: Galaxy S23

-- accessory: mouse with DPI of at least 3000
SELECT name, attributes ->> 'dpi' AS dpi
FROM products
WHERE category = 'accessory'
  AND (attributes ->> 'dpi')::int >= 3000;
-- result: Wireless Mouse | 4000

-- audio: noise cancelling headphones
SELECT name, attributes ->> 'battery_hours' AS battery_hours
FROM products
WHERE category = 'audio'
  AND (attributes ->> 'noise_cancelling')::boolean;
-- result: Noise Cancelling Headphones | 30
```

Each query filters on a key that exists only in that category (`cpu`/`ram_gb`, `pages`, `has_5g`, `dpi`, `noise_cancelling`), not on `name`, `category` or `price`. `->>` gives text, so it is cast (`::int`, `::boolean`) before comparing.

## Task 4 — Containment query

```sql
-- find any product where a given key/value exists inside attributes
SELECT name FROM products WHERE attributes @> '{"wireless": true}';
```

Result:

| name |
|---|
| Wireless Mouse |
| Noise Cancelling Headphones |

`@>` checks that the JSON on the left contains everything in the JSON on the right. It works across categories, so it finds both products.

## Task 5 — Update JSONB without altering the table

```sql
-- add a new attribute to one existing row, no ALTER TABLE needed
UPDATE products
SET attributes = attributes || '{"discount_pct": 10}'
WHERE name = 'Wireless Mouse'
RETURNING name, attributes;
```

Result: `Wireless Mouse | {"brand": "Logitech", "dpi": 4000, "wireless": true, "discount_pct": 10}`

`||` merges the two JSON objects. Only this row gets the new key; the other rows and the table structure stay unchanged. Other useful forms:

```sql
-- set or change one key (works for nested keys too)
UPDATE products SET attributes = jsonb_set(attributes, '{discount_pct}', '15') WHERE name = 'Wireless Mouse';

-- remove a key
UPDATE products SET attributes = attributes - 'discount_pct' WHERE name = 'Wireless Mouse';
```

## Task 6 — Index and compare

**Step 1 – with only 5 rows the planner will always choose a sequential scan** (it is cheaper than using an index), so first add more data to see a real difference:

```sql
INSERT INTO products (name, category, price, attributes)
SELECT 'Item ' || g,
       'accessory',
       (random() * 1000)::numeric(10,2),
       jsonb_build_object('wireless', (g % 100 = 0), 'dpi', 800 + (g % 5) * 800)
FROM generate_series(1, 200000) AS g;

ANALYZE products;
```

**Step 2 – run `EXPLAIN ANALYZE` before the index:**

```sql
EXPLAIN ANALYZE
SELECT name FROM products WHERE attributes @> '{"wireless": true}';

EXPLAIN ANALYZE
SELECT name FROM products
WHERE category = 'laptop' AND (attributes ->> 'ram_gb')::int >= 16;
```

**Step 3 – create the index and run both again:**

```sql
-- index the jsonb column
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);
ANALYZE products;

EXPLAIN ANALYZE
SELECT name FROM products WHERE attributes @> '{"wireless": true}';

EXPLAIN ANALYZE
SELECT name FROM products
WHERE category = 'laptop' AND (attributes ->> 'ram_gb')::int >= 16;
```

**What you should see (paste your own timings in the table):**

| Query | Before index | After GIN index |
|---|---|---|
| `attributes @> '{"wireless": true}'` | `Seq Scan on products` with `Filter: (attributes @> ...)`, reads all rows | `Bitmap Heap Scan` on `products` using `Bitmap Index Scan on idx_products_attributes`, much lower execution time |
| `(attributes ->> 'ram_gb')::int >= 16` (Task 3 style) | `Seq Scan` | **No change**, still `Seq Scan` — the GIN index cannot be used for `->>` with `>=` |

**Conclusion:** the GIN index greatly speeds up containment (`@>`) and key-exists (`?`) queries. The Task 3 queries that use `->>` plus a cast are not helped by it. To speed those up, either rewrite them with `@>` for equality checks (e.g. `attributes @> '{"has_5g": true}'`), or add a B-tree expression index:

```sql
CREATE INDEX idx_products_ram ON products (((attributes ->> 'ram_gb')::int));
```

Also check the index size with `\di+ idx_products_attributes` to see the extra disk space GIN needs.

**Differences noted**

| Point | PostgreSQL + `jsonb` | MongoDB |
|---|---|---|
| **Syntax** | SQL with JSON operators (`->>`, `@>`, `||`). Values pulled with `->>` are text, so a **cast** (`::int`) is needed for numbers. | JavaScript-style query objects (`{ $gte: 16 }`). Numbers stay numbers, **no cast** needed. |
| **Querying nested data** | `attributes -> 'specs' ->> 'cpu'` | `"attributes.specs.cpu"` (simple dot notation) |
| **Indexing** | One GIN index covers `@>`/`?` on every key; range queries on one key need a separate B-tree expression index. | A normal index per field, or a **wildcard index** (`$**`) to cover all keys in a sub-document. Range queries on indexed fields work directly. |
| **Updates** | `attributes \|\| '{...}'` or `jsonb_set(...)`; the whole `jsonb` value is rewritten. | `$set` changes one field in place. |
| **Schema and joins** | Typed columns plus constraints; joins with other tables are easy. | Flexible documents; joins are limited, so related data is usually embedded. |
| **Ease of use** | Easier if you already know SQL and need joins/transactions. The cast and operator syntax takes a little getting used to. | Simpler and more natural for pure document data; queries read like the data itself. |

**Final remark:** for this product catalogue both databases can do the job. PostgreSQL + `jsonb` is the better choice when products also need to be joined with orders, customers and payments in transactions. MongoDB is simpler when the data is just documents and the system needs to scale across many servers.
